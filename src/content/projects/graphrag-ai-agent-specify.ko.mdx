# Specify.app

## 문제의 출발점

의료기기 소프트웨어 인증 문서를 직접 다루면서 코드와 문서가 쉽게 어긋나는 문제를 경험했습니다. 기능과 설계가 바뀌어도 요구사항, 설계, 시험, 운영 문서는 별도로 찾아 수정해야 했고, 누락 여부를 확인하는 데 많은 시간이 들었습니다.

이 문제는 인증 시점에만 나타나지 않습니다. 신규 인력 온보딩, 고객·감사 대응, 공공·대기업 납품에서도 같은 코드-문서 불일치가 반복됩니다.

## 제품 가설

Specify.app은 코드와 업무 맥락을 연결해 SDLC 문서를 생성하고, 코드 변경이 어떤 요구사항·설계·시험 항목에 영향을 주는지 추적해 필요한 문서 수정과 승인 이력을 남기는 제품을 지향합니다.

현재 검증하는 핵심 가설은 다음과 같습니다.

- 전담 문서 인력이 부족한 소프트웨어 팀은 인증·납품 직전 문서를 한꺼번에 맞추는 과정에서 큰 재작업 비용을 겪는다.
- 단발성 문서 생성보다 코드 변경 영향 탐지, 수정 제안, 승인 기록을 통한 지속 최신화에 더 큰 운영 가치가 있다.
- 신뢰 가능한 근거와 감사 가능한 상태 전환이 단순한 AI 문서 생성보다 구매 결정에 중요하다.

## 첫 검증 고객군

초기 고객군은 국내에서 다음 조건을 동시에 가진 팀입니다.

- 10–100인 소프트웨어 기업
- 3–6개월 안에 GS 1등급 인증 또는 공공·대기업 납품 일정이 있음
- 전담 문서 인력이 부족함
- 코드 변경과 문서 수정 사이의 책임·승인 이력이 분산되어 있음

이 조건은 확정된 시장 성과가 아니라, 고객 인터뷰와 유료 약속으로 검증 중인 ICP입니다.

## 목표 워크플로우

1. 저장소의 코드, 요구사항, 기존 문서를 연결합니다.
2. 변경된 코드가 어떤 설계·시험·운영 문서에 영향을 주는지 탐지합니다.
3. 근거와 함께 수정안을 제안합니다.
4. 담당자가 검토·승인한 이력을 남깁니다.
5. 납품·인증 시점에 필요한 문서 상태와 누락을 확인합니다.

자동 생성 자체보다 사람이 검토할 수 있는 근거, 승인 경계, 변경 이력을 우선합니다.

## 사업 모델 가설

인증·납품 문서 제작 프로젝트로 문제와 데이터를 먼저 이해한 뒤, 코드 변경 영향 탐지와 문서 최신화를 제공하는 구독으로 확장하는 모델을 검증하고 있습니다. 컨설팅 파트너가 고객 프로젝트에 적용할 수 있는 채널도 함께 탐색합니다.

## 현재 상태와 증거 기준

Specify.app은 현재 시장 검증 단계입니다. 공개 페이지에는 검증되지 않은 고객 수, 전환율, 시간 절감 수치를 성과처럼 표시하지 않습니다. 다음 증거가 생길 때만 상태를 갱신합니다.

- 실제 고객 인터뷰와 반복 관찰
- 가격에 대한 구체적 반응
- 유료 파일럿 또는 구매 약속
- 사용 전후를 같은 기준으로 측정한 운영 지표
