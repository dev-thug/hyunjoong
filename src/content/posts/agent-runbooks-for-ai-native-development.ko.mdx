AI 코딩 에이전트를 도입할 때 가장 흔한 실패는 모델 성능 문제가 아니다. 실패의 대부분은 운영 방식이 비어 있을 때 발생한다. 누가 어떤 일을 맡길 수 있는지, 에이전트가 어떤 파일과 도구를 만질 수 있는지, 언제 사람에게 넘겨야 하는지, 결과를 어떻게 검증해야 하는지에 대한 규칙이 없으면 좋은 모델도 팀의 신뢰를 얻지 못한다.

그래서 AI Transformation, 즉 AIAx를 개발 조직에 적용할 때는 프롬프트 모음보다 **에이전트 런북**이 먼저 필요하다. 런북은 에이전트에게 일을 시키는 표준 절차다. 사람이 온보딩 문서를 보고 일하듯, 에이전트도 목표, 입력, 금지 사항, 검증 기준, 실패 시 행동을 명확히 받아야 한다.

이 글은 Claude Code, OpenAI Codex, 사내 자동화 에이전트를 운영하는 팀이 바로 적용할 수 있는 런북 구조를 정리한다. 특정 도구 홍보가 아니라, 에이전트를 실제 업무 흐름에 넣을 때 필요한 안전한 운영 설계에 초점을 맞춘다.

## 왜 프롬프트가 아니라 런북인가

프롬프트는 한 번의 요청을 잘 보내기 위한 문장이다. 런북은 반복 가능한 업무를 안전하게 끝내기 위한 시스템이다.

예를 들어 다음 두 요청은 겉으로는 비슷해 보이지만 결과 품질은 크게 다르다.

```text
나쁜 요청:
이 버그 고쳐줘.

좋은 런북 기반 요청:
목표: 결제 실패 후 재시도 버튼이 비활성화되는 버그를 수정한다.
범위: src/app/checkout, src/lib/payments, 관련 테스트만 수정한다.
금지: API 스키마, DB 마이그레이션, 가격 정책은 변경하지 않는다.
검증: npm run lint, npm run build, 결제 실패 케이스 단위 테스트를 통과해야 한다.
에스컬레이션: 외부 결제사 동작이 불명확하면 코드 변경 전 중단하고 조사 결과를 보고한다.
```

후자는 에이전트가 어떤 결정을 할 수 있고 어떤 결정을 하면 안 되는지 알려준다. 특히 Claude Code처럼 터미널에서 코드베이스를 읽고 파일을 수정하는 도구는 공식 문서에서도 설정과 권한, 훅을 통해 동작을 제어할 수 있음을 설명한다. Anthropic의 Claude Code 문서는 사용자 및 프로젝트 설정을 분리하고, hooks로 명령 실행 전후 동작을 정의할 수 있다고 안내한다. 참고: [Claude Code settings](https://code.claude.com/docs/en/settings), [Claude Code hooks](https://code.claude.com/docs/en/hooks).

OpenAI Codex 역시 개발 작업을 자연어로 지시하고 코드 변경을 수행하는 에이전트형 워크플로우를 전제로 한다. 공식 Codex 페이지는 코딩 작업 위임과 코드베이스 작업을 중심에 둔다. 참고: [OpenAI Codex](https://developers.openai.com/codex).

도구가 강력해질수록 팀이 설계해야 하는 것은 더 긴 프롬프트가 아니라 더 좋은 운영 경계다.

## 에이전트 런북의 7가지 구성 요소

실무에서 효과가 좋았던 런북은 다음 7개 블록으로 구성된다.

### 1. 업무 유형

먼저 에이전트가 처리할 업무를 분류한다.

- 읽기 전용 조사: 로그, 코드, 문서 분석
- 작은 수정: UI 문구, 타입 오류, 린트 오류, 단일 버그
- 기능 구현: API, 화면, 상태 관리, 테스트 포함
- 운영 작업: 배포 확인, CI 실패 복구, 릴리즈 노트 작성
- 위험 작업: 인증, 결제, 권한, 데이터 삭제, 마이그레이션

모든 업무를 같은 방식으로 맡기면 안 된다. 읽기 전용 조사는 자동화해도 부담이 작지만, 결제 로직 수정은 사람의 승인 지점이 필요하다.

### 2. 입력 계약

에이전트에게 줄 입력을 표준화한다.

```text
업무명:
목표:
배경:
수정 가능 파일:
수정 금지 파일:
참고 문서:
성공 기준:
검증 명령:
보고 형식:
```

이 형식은 단순하지만 강력하다. 특히 `수정 금지 파일`과 `성공 기준`은 에이전트의 과잉 수정을 줄인다.

### 3. 권한 경계

에이전트가 도구를 사용할 수 있다고 해서 모든 도구를 항상 허용해야 하는 것은 아니다.

권한은 세 단계로 나누면 운영하기 쉽다.

| 단계 | 허용 작업 | 예시 |
| --- | --- | --- |
| Read | 읽기만 허용 | 코드 검색, 로그 확인, 문서 요약 |
| Write | 제한된 파일 수정 | 컴포넌트 수정, 테스트 추가, MDX 작성 |
| Execute | 명령 실행 및 배포 관련 작업 | lint, build, CI 확인, PR 생성 |

팀의 기본값은 Read에서 시작하는 것이 좋다. 반복적으로 안전성이 확인된 업무만 Write와 Execute로 올린다.

### 4. 검증 기준

에이전트의 산출물은 말이 아니라 실행 결과로 검증해야 한다.

최소 기준은 다음과 같다.

- 코드 변경: lint, typecheck, build 또는 관련 테스트
- 문서 변경: 링크, 제목, 메타데이터, 렌더링 가능성 확인
- 운영 변경: 실제 명령 출력, 배포 상태, 롤백 방법 기록
- 데이터 변경: 샘플 입력과 출력, 변경 전후 diff, 복구 계획

검증 명령을 런북에 넣어두면 에이전트가 작업을 끝냈다고 주장하기 전에 스스로 확인하게 만들 수 있다.

### 5. 에스컬레이션 조건

좋은 에이전트는 모든 것을 자동으로 처리하는 에이전트가 아니다. 멈춰야 할 때 멈추는 에이전트다.

에스컬레이션 조건은 구체적으로 써야 한다.

- 요구사항이 충돌한다.
- 인증, 결제, 개인정보, 데이터 삭제 로직을 건드려야 한다.
- 테스트는 통과하지만 사용자 경험이 바뀐다.
- 외부 API 문서와 실제 동작이 다르다.
- 빌드 실패 원인이 이번 변경과 무관한 것처럼 보인다.
- 세 번 이상 같은 방식으로 실패한다.

이 조건을 명시하면 에이전트가 불확실한 상황에서 임의로 결정을 확장하는 것을 막을 수 있다.

### 6. 산출물 형식

에이전트가 최종 보고를 어떻게 해야 하는지도 런북에 포함한다.

```text
요약:
변경 파일:
검증 결과:
남은 리스크:
사람이 확인해야 할 부분:
```

이 형식은 리뷰어의 시간을 줄인다. 특히 `남은 리스크`가 중요하다. 에이전트가 자신이 검증하지 못한 부분을 명시하면 팀은 더 빠르게 판단할 수 있다.

### 7. 피드백 루프

런북은 한 번 만들고 끝나는 문서가 아니다. 실패 사례를 반영해 계속 업데이트해야 한다.

예를 들어 에이전트가 자주 하는 실수가 다음과 같다면 런북에 직접 추가한다.

- 테스트 없이 UI만 수정한다.
- 기존 컨벤션 대신 새로운 유틸을 만든다.
- 문서 링크를 확인하지 않는다.
- 타입 오류를 `any`로 덮는다.
- CI 실패를 환경 문제로 단정한다.

런북 업데이트는 AIAx의 핵심이다. AI를 도입하는 것이 아니라, AI가 안정적으로 일할 수 있도록 조직의 작업 방식을 바꾸는 것이다.

## 예시: 코딩 에이전트용 버그 수정 런북

아래는 그대로 복사해서 팀에 맞게 바꿀 수 있는 예시다.

```text
역할:
너는 우리 저장소의 버그 수정 에이전트다. 작은 범위의 결함을 원인 분석, 수정, 검증까지 수행한다.

목표:
보고된 버그를 재현 가능한 원인으로 설명하고, 최소 변경으로 수정한다.

입력:
- 버그 설명
- 예상 동작
- 실제 동작
- 관련 파일 또는 화면
- 재현 단계

작업 절차:
1. 변경 전 코드와 기존 테스트를 읽는다.
2. 원인을 한 문단으로 정리한다.
3. 수정 범위를 제안한다.
4. 최소 변경을 적용한다.
5. 관련 테스트를 추가하거나 기존 테스트를 보강한다.
6. lint, typecheck, build 또는 지정 테스트를 실행한다.
7. 결과와 남은 리스크를 보고한다.

금지:
- 관련 없는 리팩터링
- API 계약 변경
- 데이터베이스 스키마 변경
- 인증, 결제, 권한 정책 변경
- 실패한 검증을 성공처럼 보고하기

에스컬레이션:
- 재현이 불가능하면 수정하지 말고 조사 결과를 보고한다.
- 외부 서비스 동작이 원인일 가능성이 있으면 문서와 로그를 확인한 뒤 중단한다.
- 같은 검증이 세 번 실패하면 더 이상 자동 수정하지 않는다.
```

이 정도만 있어도 에이전트의 작업 품질은 크게 달라진다. 핵심은 모델에게 더 많은 자유를 주는 것이 아니라, 좋은 개발자가 일하는 순서를 명시하는 것이다.

## Claude Code나 Codex에 적용할 때의 팁

도구별 차이는 있지만 원칙은 비슷하다.

### Claude Code

Claude Code를 팀에서 쓴다면 프로젝트 단위 설정과 반복 명령을 적극 활용하는 것이 좋다. 공식 문서의 settings와 hooks 개념을 보면, 프로젝트별 설정과 명령 실행 전후 훅을 통해 팀 표준을 강제할 수 있다. 예를 들어 위험한 쉘 명령을 막거나, 작업 종료 후 lint를 실행하도록 구성할 수 있다.

실무 팁은 다음과 같다.

- 저장소 루트에 에이전트 작업 규칙을 문서화한다.
- 반복 작업은 slash command나 팀 템플릿으로 만든다.
- 훅은 보안 장치로 사용하되, 모든 검증을 훅에만 의존하지 않는다.
- 에이전트가 실행한 명령과 결과를 최종 보고에 남기게 한다.

### Codex

Codex류 에이전트에는 작업 단위를 작게 주는 것이 중요하다. 하나의 요청에 설계, 구현, 테스트, 배포, 문서화를 모두 넣으면 실패 시 원인을 추적하기 어렵다.

권장 단위는 다음과 같다.

- 조사 태스크: 변경 없이 원인과 옵션만 보고
- 구현 태스크: 승인된 옵션만 코드로 반영
- 검증 태스크: 테스트와 빌드 결과만 확인
- 정리 태스크: PR 설명, 릴리즈 노트, 운영 메모 작성

이렇게 나누면 사람은 중요한 의사결정에 집중하고, 에이전트는 반복 작업을 안정적으로 처리한다.

## 운영 지표: 에이전트가 정말 도움이 되는가

에이전트 도입 효과를 감으로 판단하면 과장되기 쉽다. 다음 지표를 월 단위로 보면 실제 개선 여부를 확인할 수 있다.

- 에이전트가 초안 작성한 PR 수
- 사람이 다시 작성한 코드 비율
- CI 첫 통과율
- 리뷰 코멘트 중 요구사항 오해 비율
- 평균 버그 수정 리드타임
- 에스컬레이션 후 해결까지 걸린 시간
- 에이전트 작업으로 발생한 회귀 버그 수

좋은 지표는 에이전트를 더 많이 쓰는지가 아니라, 사람의 재작업이 줄고 품질이 유지되는지를 보여줘야 한다.

## 팀 도입 순서

처음부터 모든 개발 업무를 에이전트에게 맡기지 말자. 다음 순서가 안전하다.

1. **문서와 코드 조사**: 변경 없이 분석만 시킨다.
2. **테스트 보강**: 기존 동작을 명확히 표현하게 한다.
3. **작은 버그 수정**: 단일 파일 또는 단일 기능 범위에서 시작한다.
4. **CI 실패 복구**: 로그 기반으로 제한된 수정만 허용한다.
5. **기능 구현 보조**: 사람이 설계한 작업을 작은 단위로 위임한다.
6. **운영 자동화**: 검증과 롤백 절차가 있는 작업만 자동화한다.

이 순서는 신뢰를 쌓는 순서이기도 하다. 팀이 에이전트를 신뢰하려면 성공 경험보다 실패했을 때의 안전장치가 먼저 보여야 한다.

## 마무리

AI 네이티브 개발은 개발자가 사라지는 것이 아니라, 개발자의 업무 운영 방식이 바뀌는 것이다. 좋은 팀은 에이전트에게 막연히 일을 던지지 않는다. 업무 유형을 나누고, 입력 계약을 만들고, 권한을 제한하고, 검증을 실행하고, 멈춰야 할 조건을 정의한다.

프롬프트는 시작점이다. 런북은 운영 체계다. AIAx를 진지하게 추진하는 팀이라면 오늘 당장 하나의 에이전트 런북을 만들고, 작은 업무 하나에 적용해보자. 반복 가능한 절차가 쌓일수록 에이전트는 데모가 아니라 팀의 실제 생산성 시스템이 된다.
